# Workshop Hackathon — a narrow Event subtype

A Hackathon stays one canonical Workshop Event: one page at `/g/:group/e/:slug`, one RSVP, one waitlist, the same four tabs, the same capacity + overflow ceiling. The only new behavior is a team layer that rides on top of the existing RSVP.

## What people will see

**Admin.** In the existing Events composer, picking Kind = "Hackathon" locks Attendance to Online, marks it first-party, disables recurrence, requires capacity, and reveals a "Hackathon setup" section: number of teams (2–20), full-group meeting time, the full-group room URL (the Event's existing Online URL), and one editable name + room link per generated team. A live summary reads like "4 teams · 20 intended participants · about 5 per team · 5 overflow · up to 25 RSVPs accepted". Incomplete setup saves as a draft; publishing is blocked until every team has a room link and the full-group time and URL are valid. A "Manage Hackathon" control on Hackathon rows opens a control room with counts, rooms-ready status, per-team rosters, editable links, admin open-room actions, and a move-participant control.

**Participant.** They find the Hackathon like any other Event and RSVP with the normal button (no plus-ones offered). The moment the RSVP succeeds a panel appears under the RSVP block, above the tabs: "Your team — Team 3 · 5 participants", a Join Team 3 room button, their teammates' avatars, the full-group meeting time, and a Join full-group room button. Before the Event, the schedule leads; once it starts, the team room is the primary button; at the full-group time, the full-group room takes over. Waitlisted people see "A team will be assigned if a spot opens." Logged-out or non-RSVP'd visitors see only "You'll be assigned automatically to one of 4 evenly sized teams when you RSVP" — never a link, never a roster.

## Technical approach

**Wave 1 — schema and vocabulary.** Forward migration adding `hackathon` to the `group_event_kind` enum; three additive tables keyed to `group_events.id`: `event_hackathons` (event_id PK, `full_group_meeting_at`, timestamps), `event_hackathon_teams` (unique `(event_id, position)`, `name`, nullable `meeting_url`), `event_hackathon_assignments` (PK `(event_id, user_id)`, `team_id` with a composite FK guaranteeing the team belongs to the same Event, `assignment_source` in `automatic|admin`, `assigned_by`). All cascade from the Event. GRANTs plus RLS: `anon`/`authenticated` may read team `id/position/name` and assignment counts only — never `meeting_url`; all writes are service-role/server-authorized; participants read their own team through the protected server path. Mirror `hackathon` into `EVENT_KINDS`, `KIND_LABELS`, admin Zod schemas, event filters, and regenerate `src/integrations/supabase/types.ts`.

**Wave 2 — assignment and access.** A trigger on `group_event_rsvps` (after insert/update of status) calls a security-definer function that: no-ops unless an `event_hackathons` row exists; treats `going`/`maybe` as attending, matching `access.server.ts`; locks the `event_hackathons` row to serialize; inserts into the least-populated team, ties broken by lowest `position`; keeps an existing assignment when an attending RSVP is merely updated; deletes the assignment on `waitlist`/`declined`/`canceled`; reassigns on waitlist→attending promotion. This lives inside the existing `reserve_event_rsvp` transaction, so the assignment exists before the mutation returns. `reserve_event_rsvp` keeps sole authority over the capacity + overflow ceiling and waitlisting; it also forces `plus_ones = 0` for configured Hackathons. New server functions in `src/lib/events/hackathon.functions.ts`: a public-safe config read (team count and full-group time only), `getMyHackathonParticipation` (own assignment, own team roster, own room URL, full-group URL only when `canSeeOnlineUrl`), an admin state read, and admin mutations for configure, edit team, and move participant — all resolving permission through `requireEventAccess`/`resolveEventAccess`, never a new host check.

**Wave 3 — admin UI.** Extend `src/routes/admin.events.tsx` and `group-events-admin.functions.ts`: conditional setup section, capacity/team-count/time/URL validation on client and server, `assertPublishable` extended with Hackathon gates (config exists, ≥2 teams, capacity ≥ team count, valid full-group time inside the Event window, full-group URL, every team room URL, not recurring). Orchestration is draft → configure → gated publish, reusing `createEvent`/`publishEvent` so the new-Event notification fires exactly once. The control room is a dialog inside the existing Admin Events surface; populated teams cannot be deleted, added teams do not reshuffle existing people.

**Wave 4 — Event page.** A `HackathonPanel` rendered conditionally between `EventRsvpBlock` and the tabs in `g.$slug.e.$eventSlug.tsx`. No fifth tab, no second RSVP mutation; the RSVP mutation invalidates the participation query so the team appears immediately. For configured Hackathons the location card stops rendering a competing join button and its prompt reads "RSVP to get your team and room links." All times render through the existing timezone-aware utilities.

**Wave 5 — verification.** Unit tests for the publish gates and CTA-priority logic; database tests for balanced sequential assignment (4/3/3), concurrent RSVPs not double-assigning, cancel/promote transitions, and populated-team deletion refusal; access tests proving logged-out, non-RSVP'd, waitlisted, and other-team viewers get no URLs, and that public DTOs, `getEventBySlug`, OG metadata, ICS, and notifications stay clean. Then typecheck, the existing suite, a production build, and responsive QA of the composer, control room, and the four viewer states. Any pre-existing failure will be called out separately from regressions.

## Explicitly not building

No `/hackathons` route, no second RSVP or application, no participant-chosen or skill-matched teams, no per-team capacity, groups, collabs, chats, walls or galleries, no Zoom/OAuth/auto-generated links, no recurring Hackathons, no plugin framework, and no changes to normal Events, Open House, or venue behavior. An external Event with `kind = 'hackathon'` and no configuration row stays an ordinary external Event.
